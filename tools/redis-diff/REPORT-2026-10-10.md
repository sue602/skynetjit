## Five real defects the differential found, all fixed

Every one of them is a case the smoke test could not see, because the smoke test
compares the library against its own expectations while this compares it against
Redis.

1. **`ZRANK` / `ZREVRANK` aborted the process.** `zsetRank()` starts at the
   listpack's first entry and asserts one exists (`t_zset.c:1816`). A server cannot
   reach that assert: a sorted set with no members is a missing key there, and
   `ZRANK` of a missing key replies nil. A handle that emptied out stays
   addressable here, so `zrank` after removing the last member crashed. Fixed by
   answering the nil reply before the walk (`facade/sortedset.c`).
2. **`ZRANDMEMBER <count>` on an emptied handle dereferenced a null dict entry.**
   Upstream's guard is the `lookupKeyReadOrReply(..., shared.emptyarray)` that a
   missing key takes. The counted path now answers the empty array first (the
   single-element form already answered nil); cases with `count >= size` and the
   negative-count form reach the kernel's samplers, which all require a non-empty
   set.
3. **`BITPOS` replied `false` where Redis always answers a number.** Three paths
   were wrong, all inherited from modelling an empty object as "no key → nil":
   a missing key is "an infinite array of 0 bits" and answers `bit ? -1 : 0`
   (`bitops.c:884`); an empty range answers -1 (`:890`); and a scan that found
   nothing answers -1, never nil (`result:`). Fixed in `facade/bitmap.c`.
4. **`PFMERGE` dropped the destination's own registers.** Upstream's merge loop runs
   from `argv[1]`, which *is* the destination key, so `PFMERGE dest src` keeps
   what `dest` held and `PFMERGE dest dest` is the documented no-op. The facade
   iterated only the source list, so cardinality was silently lost — caught as
   `state.count: 56 != 39` in the diff. Fixed by starting the iterator at the
   receiver (`facade/hll.c`).
5. **`GEORADIUSBYMEMBER` / `GEOSEARCH FROMMEMBER` raised where Redis answers the
   empty array.** `longLatFromMember()` failing is a genuine error, but only for a
   source key that *exists*: for a missing one, upstream skips the resolution
   (`geo.c:541`, `geo.c:624`) and takes its "return ASAP" path (`geo.c:698`),
   which replies the empty array — or 0 and a cleared destination, with `STORE`.
   An empty geoset is that missing key here, so the same route is now taken
   (`facade/geo.c:rl_geo_member_or_empty`), while a member missing from a
   non-empty geoset still raises the error.

## Harness bugs found on the way (the tooling, not the port)

Recording these because a differential harness is only as trustworthy as its own
mapping, and each of them produced a plausible-looking false positive:

* `PFDEBUG` puts its subcommand *before* the key; the first replay sent
  `PFDEBUG key subcommand`, which made the server look up a key named `todense`
  and error. This is what the "dense body of zeros vs sparse bytes" mystery at
  seq 118 really was.
* `ZRANGESTORE`'s source is one name, not a list; a shared code path indexed a
  string as if it were a table and sent `ZRANGESTORE zset_6 z …`, so the server
  stored from a key that did not exist (48 false differences).
* The exchange files carried raw bytes in JSON, which is not legal; they are hex
  now, which also makes them inspectable.
* A round-trip check (`load(dump(x)) == x`) was asserted *after* a `PFCOUNT`, and
  PFCOUNT caches its estimate inside the value — Redis does the same thing, which
  the interop step now asserts as a positive check ("both sides cache the same
  bytes").

## What the interop step proves (spec §4)

Both directions, on a live server:

* a sketch built with 400 `PFADD`s, `GET`'d from the server, `hll.load`ed here:
  loads byte-identically, counts the same, and after each side runs its own
  `PFCOUNT` the two values are **the same bytes** (the cardinality cache agrees);
* a string value built with `SETBIT`, `GET`'d and `bitmap.load`ed: same
  `BITCOUNT`, same `BITPOS`, `dump()` returns the identical bytes;
* the library's `dump()` of a bitmap and of an HLL `SET` into the server: the
  server's `PFCOUNT`/`BITCOUNT` match what the library counted;
* a sorted-set blob and a geoset blob, parsed in Python with `struct` only (no
  Redis code, which is spec §4's "any language" claim) and replayed with `ZADD`:
  `ZCARD`, the full `ZRANGE … WITHSCORES`, and `GEODIST` of the replayed geoset
  (`166.2742` km) all agree with the library.

## Excluded from comparison, on purpose

* `ZRANDMEMBER`'s reply: Redis' own random sample. Its *state* is still compared.
* `no-command-table` (8 ops): a command too short for Redis' `arity` field is
  rejected before its handler, and this port has no command table, so the
  handler's own error text appears. Both sides error; the texts differ.
* `no-keyspace`: `PFDEBUG` on a key that was never created errors on a server and
  runs here, because the handle exists. This one is **not generated** -- unlike the
  arity case it is not a one-record difference: the server refuses a state-changing
  `PFDEBUG TODENSE` that the library performs, so the two objects then differ for
  the rest of the run and every later probe of that key reports a cascade of the
  same fact. `gen.lua` therefore issues `PFDEBUG` only for keys the log has already
  written on both sides (see its comment), and the deviation is asserted in the
  smoke test instead.
* `ZSCAN` and the blocking family are not part of the port, so they are not
  generated.

Those two classes are named in `diff.py` and counted separately, so a new kind of
difference cannot slip into them: any record that is not exactly one of them is
reported as unexplained and makes the exit code nonzero.
